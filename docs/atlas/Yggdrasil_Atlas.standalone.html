Yggdrasil

Automate anything: traceable plans, reproducible runs.

When something changes in a system it watches, Yggdrasil writes down an explicit plan, waits for approval where one is required, runs the plan step by step, and keeps the evidence.

  • CrownRealms: one domain’s logic each, shipped as plug-ins.
  • TrunkThe core daemon: watches, routes, runs. It knows no domain.
  • RootsDurable state: plans, snapshots, checkpoints, files.

  1. Watch

    core

    A watcher notices a change in an external system.

    → event

  2. Plan

    realm handler

    The realm turns the change into an explicit plan for one scope: steps and their dependencies.

    → plan draft

  3. Approve

    a person, or the realm

    The plan waits as a document until this exact version is approved.

    → approved plan

  4. Run

    engine + realm steps

    Steps run in dependency order. A step whose earlier result is still valid is reused.

    → attempt

  5. Record

    core → stores

    The result is written back onto the plan, and a status snapshot is published.

    → result + snapshot

          Rules that hold everywhere

          The whole design compressed into a dozen statements. If a behaviour surprises you, one of these usually explains it.

          • Handlers plan, the engine runs

            A handler returns intent. Execution always goes through the stored plan, so there is exactly one execution path.

          • A plan is a document

            One document per plan ID. What it says will run is the execution definition; changing that means a new generation.

          • Approval is bound to a generation

            Regenerating a plan resets its status and tokens. An approval never carries over to a version nobody saw.

          • Status is approval, never outcome

            status stays approved after a run, however it went. The outcome lives in last_finalized_execution.

          • Eligible means approved and owed a run

            run_token above executed_run_token. Raise run_token to ask again. Equal tokens mean finished, not succeeded.

          • Every decision comes from one fresh read

            Never from the event that prompted it. A stale event cannot pair an old approval with a newer plan.

          • Results are recorded conditionally

            Outcome and executed token are written together, on the revision that was read, and never onto another generation.

          • Only dependencies order and block

            No step is special for its name or position. A failed step blocks exactly the steps that depend on it.

          • Reuse needs proof

            A matching fingerprint and every declared output present. Otherwise the step runs again in the same directory, and must tolerate that.

          • Unknown stays unknown

            Nothing is defaulted or converted. A document outside the supported family is shown, never executed or approved.

          • Two event systems

            Trigger events decide which handler plans. Step events record what an attempt did. They never mix.

          • The core knows no domain

            Everything specific lives in a realm. Internal state sits behind one storage interface; realm data behind DataAccess.

          Around the loop

          Start-up

          Configuration is resolved from YGG_HOME. Realms are discovered through the ygg.realm entry point, and their handlers and WatchSpecs are checked: a wiring mistake stops the daemon before it starts. One daemon runs per mode, per user, per host.

          Two ways in

          yggdrasil daemon runs the loop until stopped. yggdrasil run-doc handles one document: plan only, or plan and execute in the same process with --run-once. A run-once session executes only the plans it created.

          The published contract

          yggdrasil.contract holds the JSON Schemas, the version and token checks, and the shared reader. Any program that reads plan documents or snapshots can reach the same conclusions as the daemon.

          Dev mode

          --dev swaps in the dev configuration, enables the built-in test realm, allows one SQLite file for internal state, and defaults to separate work and spool directories, so a dev daemon can sit beside production.
